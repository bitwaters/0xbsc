## 问题与范围

研究记录逐事件调用 dbstat，同步遍历约 749 MB 研究页面，线上单次测量约 472 ms。50 条候选重复扫描就可能消耗约 24 s。研究记录虽不增加 API 请求，仍阻塞正式业务的事件循环。这是此前隔离实现和验证遗漏。

本次不修改筛选阈值，不开启新策略，不改写历史信号卡片、确认价格或结果数据。提案进度仍为 30/39，新正式发布器与独立验证尚未完成。

## 修复

- 被动记录启动时在 worker 中测量容量，逐事件/事实使用保守增量预留，每分钟由 worker 校准；校准保留采样开始后所有新增预留，失败不释放预留。重复物理事实不重复计费，已知候选只预留固定字段更新开销。保持容量限制与明确的停止原因。
- 归档文件读写和页面扫描转移至 worker；维护不重叠、有 30 s 上限。研究事件逐条让出事件循环，退出时停止待处理队列；校准不可用只停止研究记录，不终止正式进程。
- 采样重排复用 prepared statement，消除逐行重新编译 SQL。
- 正式 GMGN 请求将共同截止时间传入物理传输，排队消耗同一时间预算；握手阶段同样受绝对超时限制，过期成功响应不得当成新鲜数据。排队过期记录为 queue_timeout，响应中断及时释放在途资源。
- 非 2xx 记录脱敏的响应分类、请求标识、服务端日期和响应类型；不保存任意响应正文或凭据。401 的来源需要部署后证据，不能仅凭状态推断密钥无效。
- 健康文件与分钟指标增加事件循环延迟、候选安全处理进度、影子更新时间和端点最后成功时间。Docker 健康检查同时检查业务 degraded 状态；没有信号本身不判故障，持续数据停滞和事件循环阻塞才判故障。

容量预留仍是保守估算，校准使用实际研究表/索引页及登记归档字节。非记录器的离线研究工具继续进行实际容量检查。本次线上验收针对当前 observe 模式，不代表 collect/execute_shadow 的完整负载或晋级验证通过。
