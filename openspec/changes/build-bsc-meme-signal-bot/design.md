## Context

当前目录只有经过真实 GMGN OpenAPI 脱敏审计的脚本、审计结果和 v1.4 开发方案，没有既有应用代码或 OpenSpec 能力规范。当时的脱敏审计结果（仅本地留存）覆盖 72 个测试项：68 项通过，Signal Type 14/15/16 被生产接口拒绝，订单查询因没有真实 `order_id` 跳过；没有执行交易、策略创建/取消或发币等写操作。完整业务边界见 [proposal.md](proposal.md)，详细行为合同见本变更的六份 specs。

设计受以下条件约束：市场、钱包与可执行性数据只能来自 GMGN OpenAPI；Plus 套餐服务端权重 20/s；机会窗口以分钟为主、强叙事以小时为上限；Phase 1 只推送信号；全部参数集中在一份 YAML；项目必须保持单进程、单数据库、单容器且易维护。

## Goals / Non-Goals

**Goals:**

- 用一个可观测的加权调度器同时保证发现覆盖、正式候选低延迟和结果任务不干扰实时链路。
- 用一套事件、Episode 和确定性规则覆盖新币启动、老币复苏、趋势延续，而不复制三套流水线。
- 让所有正式信号能够从来源事件追溯到安全快照、评分、双向 Quote、配置版本、Telegram 确认和结果样本。
- 通过模块边界、固定协议逻辑和集中参数保持实现小而清晰。

**Non-Goals:**

- 不设计下单、签名、私钥、资产组合或自动交易风控。
- 不引入外部市场 API、WebSocket 替代源、外部社交语义分析或人工管理后台。
- 不以机器学习、表达式 DSL、微服务或分布式消息队列替代明确规则。
- 不承诺 Telegram 严格 exactly-once，也不把有限审计样本当作稳定 P95。

## Decisions

### 1. 单进程分层事件流水线

进程内划分 `config`、`gmgn`、`discovery`、`decision`、`delivery`、`evaluation`、`storage` 七个模块。发现轮询器只产生标准事件；同一代币的事件通过带键串行队列修改 Episode，不同代币允许并发。判定链固定为低成本过滤 → Info/Security/Pool → Kline 与路线 → 按需深度数据 → 评分 → 安全刷新与双向 Quote → Outbox。

每个轮询器和响应适配器使用独立错误边界；单一来源超时、业务错误或 schema 漂移只能终止该轮任务，不能使进程或其他实时链路失败。错误状态由统一调度器施加退避，但不增加独立熔断服务。

选择原因是它保留并发 I/O 和每代币确定性，同时避免微服务、跨进程锁与消息基础设施。备选的“每来源独立流水线”会重复安全和评分逻辑，也更容易对同一代币重复推送，因此不采用。

### 2. 全局加权 Token Bucket 加优先队列

所有 GMGN 调用只能经一个调度器。Token Bucket 使用 20/s 突发上限和默认 14/s 持续软上限；任务携带端点权重、优先级、最晚有用时间和不可重入键。互不依赖的同批请求并行，卖出 Quote 等待对应买入数量。

默认发现调度为：Signal 2s/5s 两组、Trenches 5s、SmartMoney 2s、KOL 3s、Trending 1m/5m/1h 各 5s、Hot 短周期批量 15s/长周期批量 60s、Gas 30s。它对应约 147 请求、265 权重/分钟；满 60 个观察 Episode 复评约 360 权重/分钟，剩余约 215 权重/分钟，按 31 权重/完整候选估算约 6–7 个/分钟。它只描述容量，不构成推送配额。

优先级为：正式候选安全/Quote、实时发现、活动观察复评、结果采样。预算不足时，截止时间已过的实时任务直接成为陈旧样本，不保留长队。备选的固定并发数无法表达 GMGN 不同端点权重，故不采用。

### 3. 一个事件模型和一个 Episode 聚合器

标准事件保存原来源身份、标准化哈希、来源与采集时间、证据族、强度、TTL 和可选脱敏原始 JSON。稳定 ID 做直接精确去重；快照以持久化哈希和本地变化序号识别变化。活动 Episode 唯一键为 `chain + token + route`，同一证据族仅保留当前最强有效项。

这避免构造无法验证的跨 API“同一市场事件”指纹。跨来源只聚合，不强行去重；族上限和唯一 Episode 防止重复加分与重复推送。

### 4. 前置安全过滤与惰性深度调用

第一层使用事件字段及缓存，不发请求；第二层并行请求 Info/Security/Pool。任何安全关键缺失先短暂重查，仍不明确则停止。只有通过安全与触发门槛的候选才请求 Holders、Traders、Created Tokens；后续仅在“刷新后可能达到正式条件”时更新过期深度缓存。

惰性深度策略必须全部由唯一 YAML 配置。硬 veto 默认值为：非池地址单一持仓不高于 20%、可疑持仓累计不高于 10%、创建者直接持仓不高于 10%；对 GMGN `tags`/`maker_token_tags` 命中配置标签的钱包，三个及以上钱包各自卖出至少 5% 且累计至少 20% 时拒绝。创建者累计发币数本身不是门禁；只有累计创建超过 5 个且开放比例低于 50% 同时成立时，持仓与创建者质量维度从 1 降为 0.5，扣分上限为 5 分。开放比例至少 50% 时，无论累计创建数量多少均不扣分。GMGN 的百分率支持小数或百分数形式，统一规范化；池地址、创建者、标签、列表或数值无法映射时 fail closed。标签清单与阈值是可复盘的运营策略，不把 GMGN 标签本身误称为违法或诈骗判定。

该顺序既避免在最终安全失败的代币上浪费高权重资源，也不会把昂贵查询变成所有发现项的固定成本。硬安全判定是 veto，不进入加权总分；创建者历史质量调整发生在 Episode 决策与 Quote 前，调整后的总分必须重新通过 65/80 门槛。

### 5. 共享特征计算、互斥路线配置

Kline、资金流、注意力、持仓和生命周期先生成共享特征；路线分类在取得 Kline 后按固定优先级执行。每条路线只有权重、阈值、窗口和必需字段不同，使用同一三级评分器和完整度公式。趋势/沉寂等算法写在代码并由向量测试固定，数值位于 YAML。

备选的通用表达式规则引擎能提高表面灵活性，但会增加配置错误、审计难度和动态执行风险，因此不采用。

### 6. SQLite 同时承担状态、Outbox 和到期任务

使用 WAL、单写入队列、短事务和七张表：`tokens`、`events`、`episodes`、`signals`、`price_samples`、`api_stats`、`config_revisions`。可调特征与安全明细先存 JSON，只有证明确需高频查询的字段才拆列。结果采样以数据库中的 `due_at` 查询驱动，不建第二个内存池。

正式判定和 Outbox 意图同事务写入。Telegram 成功后补写 `message_id`；不确定响应进入 `DELIVERY_UNKNOWN`。单机信号规模下 SQLite 足够，并可避免 Redis、PostgreSQL、队列服务和 ORM 迁移负担。

### 7. 双向 Quote 是最终可执行性门禁

三档买入并行，随后三档卖出并行。每档使用自己实际得到的代币数量，10U 是最低必须通过档，较大档只决定显示的最大安全仓位。适配层保存原始 Quote 数量、美元估值、Gas 和语义版本；成本函数只使用已经验证的组成，避免重复扣税或费用。

Quote 返回速度决定端到端尾延迟，所以两批内部并发但不绕过依赖。推送前 Quote 过期则刷新；触发已陈旧则终止。

### 8. Telegram 采用轻量 HTTP 适配器

使用 Node 原生 HTTP 能力调用 `sendMessage`、`editMessageText`、`deleteMessage`、`answerCallbackQuery`，轮询更新只接收允许 Chat/用户的回调。消息包含稳定 `signal_id`，后续证据和结果编辑原消息。

不引入 Bot 框架可减少依赖和隐藏状态。Telegram 没有客户端幂等键，所以在响应未知时显式表达不确定性，而不是用可能丢消息的“永不重试”伪装 exactly-once。

### 9. 配置加载一次、校验一次、版本化一次

唯一 YAML 被解析后先做 schema 校验，再做跨字段校验，例如路线权重合计、观察与正式阈值顺序、Quote 档位对应限制、软硬权重关系。程序只把不可调的端点路径、协议字段映射、算法和 schema 留在代码。启动时计算去秘密的配置快照及 SHA-256，写入 `config_revisions`。

不支持 SIGHUP 热重载，避免运行中 Episode 前后使用不同参数；调参后重启单容器，旧 Episode 仍保留其配置版本。

### 10. 质量评估分离账面与可执行结果

Telegram 确认是模拟跟单起点，随后立即发起入场 Quote。Kline 用于路径、MFE/MAE 和市场收益；卖出 Quote 用于可执行收益。超时 Quote、同 candle TP/SL 歧义和无法卖出均显式标记，不能静默填充有利结果。未推送样本也安排低优先级检查点，以支持漏选分析。

每条路线至少 100 个独立正式信号后再评估稳定性；不设固定天数，避免低市场活跃期因日历时间产生虚假结论。

### 11. 高动量旧币先观察、冷却后再正式判定

生产样本表明，一部分通过安全门、具备多族证据且已经突破并保持上升趋势的旧币，会因为尚未形成“回调后重启”而在路线分类前被直接丢弃。对此不降低 80 分正式门槛，也不放宽 Quote 与安全门，而是把满足流动性、有效池、真实交易、多族证据、突破和上升趋势的旧币纳入现有 continuation 观察池。该兼容路线只授予观察资格；只有后续 Kline 已出现健康回调和重启、且不再属于垂直拉升时，才可进入正式判定。

新发币的真实交易允许“存在买单且一分钟总 swaps 为正”，不再要求同一分钟必须同时有卖单。增长条件必须由可比窗口的真实成交量加速独立证明；强资金证据仅用于资金维度。普通 Trending/Hot 排名只属于注意力证据，不伪装为叙事，也不单独满足增长。

未推送结果以 `Episode + checkpoint` 为稳定身份，正式结果以 `Signal + checkpoint` 为稳定身份，二者各自只保留一条且不互相覆盖；执行时按任务 ID 写入，防止复评改变 `fromMs` 后重复创建及批量完成。未推送样本只跟踪到 `evaluation.unsent_tracking_minutes`；正式信号仍使用全部配置检查点。Episode 的首次决策快照不可覆盖，后续复评另存 latest 快照。定时复评若最低证据过期或路线软失配，使用自第一次失配起固定的宽限期，安排下一次复评；只有新条件恢复才清除失配起点。宽限到期或 Episode 硬到期后结束，明确硬风险仍立即拒绝。

## Risks / Trade-offs

- [GMGN 未公开完整 Signal 数字类型映射或字段语义变化] → T3 用真实响应标签建立版本化映射；未知类型只存档，适配器契约测试和启动探针及时失败。
- [Plus 套餐真实限频可能与展示值或短时行为不同] → Token Bucket 留 30% 持续余量，记录 429 和服务端冷却；T14 在受控预算内做持续验收。
- [全量观察池与候选突发争抢权重] → 复评分散、低分降频、结果任务后移、实时任务带截止时间；绝不补发陈旧信号。
- [HTTP 轮询无法快于 GMGN 数据本身的发布延迟] → 同时记录 `source_event_at` 与 `observed_at`，把来源延迟和本地处理延迟分开验收。
- [当前 3/5/6/15 秒来自理论预算而非稳定真实流量] → 只用于指导并发设计；T14 分路径记录样本量、负载档位和 P50/P95/P99 后建立实测基线，校准前不作为硬发布门禁。
- [SQLite 单写者在日志过细时膨胀或阻塞] → 成功 API 只做分钟聚合、原始 JSON 可配置保留、事务短小并监控到期任务积压。
- [Telegram 响应未知造成重复或丢失二选一] → 明确 `DELIVERY_UNKNOWN`，最多一次同 ID 重试并标注可能重复，保留人工审计依据。
- [规则阈值过紧错过潜力币，过松降低命中率] → 保存未推送样本和配置版本，以固定回放集离线比较；任何调参不得改变历史结果。
- [GMGN 叙事数据不能等同全网社交情绪] → 消息和评估仅称为 GMGN 内部注意力/叙事代理，不推断外部社交语义。

## Migration Plan

1. 建立最小 TypeScript 项目、唯一配置 schema 和 SQLite migration；用空白测试配置验证无秘密可提交。
2. 在非生产 Chat 中完成 GMGN 真实契约测试、事件回放、安全和 Quote 影子判定，不发送正式信号。
3. 启用 Telegram 测试消息与 Outbox 故障注入，验证崩溃恢复、编辑、删除、回调鉴权和未知投递。
4. 以正式配置启动单容器；一旦开启正式模式，所有通过门禁且仍新鲜的信号都推送，同时监控权重、429、P95 和数据库增长。
5. 完成真实容量与延迟基线校准并确认运行阈值后，进入不限制天数的三路线样本积累。

回滚方式：停止容器并恢复上一镜像与上一份人工备份配置；SQLite migration 采用前向兼容、启动前备份。若 GMGN 合约变化，关闭受影响来源或正式推送但继续保留可解析样本，不回退或篡改历史配置版本。

## Open Questions

无会改变当前规范、架构或任务拆分的未决问题。Signal Type 映射、Kline 历史范围、Quote 成本语义和真实限频曲线是已明确归入实施期契约测试与验收的外部事实验证项。

## 2026-09-05 数据质量与筛选修订

采用路径优先的评估口径。入场价、入场时间、目标时间、观察期限和评估配置独立冻结，重试只改变下次尝试时间。升级前样本保持原值并标记 legacy；未发送和正式发送使用不同真实起点，不允许从后来展示价格补历史基准。

30s Kline 分段拉取并保留时间、粒度和完成状态。完整覆盖才报告精确上涨倍数与入场跌幅；入场跨越蜡烛、缺口和同根上下触达必须显式表达未知或界限。已能证明的首次触达不因后段缺口被改写。固定时间收益作为辅助，主要命中率分母包含完整观察后未触达者，并同时报告待观察、未知与覆盖率。

正式路线必须使用有效且新鲜的 Info、匹配池和足量连续已完成 Kline；复活路线采用滚动当前 5m 对不重叠的此前 1h 完成 5m 基线，历史 swaps 缺失单独走配置绝对门槛。协同退出通过两个同口径快照的累计买卖量和余额变化识别，不使用净收益字段的符号判断卖压。

V2 为预算受限的影子候选实验：默认买入金额占比 60%、3 个至少间隔 10 秒的采样、60 秒样本窗口、15m 内只观察。滚动样本用于持续性检验，不能当独立市场样本。资金、结构和位置分别计算；尚未经过惰性安全及 Quote 的维度保持待验证，`deliveryQualified` 始终为 false。预观察默认总量 20、优先组上限 10，其余每 60 秒复评；实际限流仍由全局调度器控制。

当前验证边界见仓库根目录 README 的 Validation status。新增影子记录不等于已经完成历史回放、可执行性实验或策略验收。

## 2026-09-06 请求治理修订

根据本地停机调查修复请求治理；调查原始资料不随公开源码发布。物理 HTTP 尝试统一在 GmgnClient 中进入 GmgnScheduler；调用方只传播优先级和不可延长的截止时间，不重复扣账。保留 Plus 20 hard / 14 soft，按权重平滑发送并额外验证本地滚动一秒硬预算，默认全局在途四个、Quote 在途一个。冷却和下一可发送时刻原子写入持久卷，按凭证哈希隔离，重启不清空服务器限制；恢复首先单请求探测。

API 错误解析保留 HTTP 状态，支持响应头和 body reset、业务限流、非 JSON 429。详情仅记录白名单字段并脱敏；每次物理尝试在 api_attempts 中保存有界诊断窗口，永久分钟统计不依赖详细日志。请求携带候选 correlation ID，候选抛错也写入 decision 审计。健康检查使用初始化后持续更新的事件循环心跳，不再只检查配置文件存在。

Traders 在访问网络前查缓存；发现与报价共享短期 Gas。结果采样保留 evaluation 用途，预观察定时器与正式观察复评分开。Quote 整组保持原始期限并以最旧腿的实际获取时刻检查新鲜度，不因串行完成而变新。上述修复不改变正式评分、安全和报价成本阈值，V2 仍为影子验证。

实际只读验收进一步复现：混合负载最高 15 权重/秒、隔离 Quote 最高 6 权重/秒仍收到 RATE_LIMIT_EXCEEDED。以配置 `gmgn.rate_limit.quote_min_interval_ms` 在同一调度器中约束 Quote 请求间隔，当前验证值 600ms，保持总权重 20/14 不变；该值是实测运行参数，不宣称官方套餐将 Quote 限定为每秒两次。保存服务端 request ID 和 reset，后续可用这些证据核实公开权重表之外的限制。

后续只读验证在 600ms Quote 间隔下仍收到 `IP rate limit exceeded`。该配置尚不能证明已解决上游 IP 限制；生产验收未通过，具体限制范围仍待确认。

## 2026-09-06 SEA 配置流程修订

按用户指定，SEA 的 config.yaml 与 .env 同处项目目录 /www/wwwroot/0xbsc，实际文件不进入 Git。策略保留在 YAML，六个运行字段由同目录 .env 覆盖并完整校验；文件只读挂载，不注入容器环境。修改源码和模板必须在本地完成，经 GitHub 推送、服务器拉取后部署。此次 SEA 使用全新数据卷，不迁移本机历史库。此要求替代早期仅允许单 YAML 的部署约束。
